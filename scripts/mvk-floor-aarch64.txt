# The aarch64 mvk-compiles ratchet floor: how many MASTER_PLAN Appendix A
# files reached ARM64 codegen at the last measurement.
# scripts/mvk-compiles.sh --arch=aarch64 fails if fewer compile than this.
#
# The rules are the x86 file's rules. Lowering this number is legitimate for
# exactly three reasons, each stated in the commit message: a file was removed
# from Appendix A, the check itself got stricter, or the compiler pin moved
# backwards deliberately.
#
# History:
#   13  first measurement, on the commit that gave the kernel backend an
#       aarch64 lowering (home-lang/home@29b9eb740).
#   62  `core/foundation.home` made architecture-neutral with `@targetIs`, and
#       five `jmp` emissions in the backend that had been left as raw x86 text
#       reached the emitter. The second of those was most of the jump: an
#       if/else in any file emitted `jmp .L_endif_N`, so almost nothing with a
#       branch in it assembled for ARM.
#
#       The 57 files that do not compile are not blocked on codegen. They are
#       blocked on the kernel source itself: `kernel/src/core/foundation.home`
#       and its callers wrap x86 instructions in `asm volatile` blocks —
#       `cli`, `sti`, `hlt`, `outb`, `cpuid`, `mov %cr3` — and inline assembly
#       is passed through verbatim by definition, so it reaches the ARM
#       assembler as x86 text and is rejected. Making those wrappers
#       architecture-neutral is home-lang/home-os#60 and #62, not compiler
#       work.
#   70  complete — every Appendix A file reaches ARM64 codegen. The last eight
#       carried their own x86 `asm volatile`: port I/O in serial.home,
#       block/io_scheduler.home and os/cpu.home; the atomics in
#       sync/spinlock.home; `invlpg` and CR3 writes in core/memory.home; the
#       stack switch in core/process.home; `pause` in drivers/timer.home; and
#       `lidt` in arch/x86_64/interrupts.home.
#
#       Three shapes of fix, and the distinction is the point:
#         - Operations both architectures have, spelled differently, became
#           neutral intrinsics (the atomics, TLB invalidation, the stack
#           pointer, the timestamp counter, a full memory fence).
#         - Operations with a real ARM64 counterpart under another name became
#           `@targetIs` pairs (CR3/TTBR0_EL1, CR2/FAR_EL1).
#         - Operations ARM64 genuinely does not have — port I/O, the GDT and
#           IDT — halt on ARM64 rather than returning a plausible value. A
#           driver that reads as working while touching no hardware is the
#           exact failure STUB(S9) exists to prevent.
#
#       x86-64 stayed at 70/70 and the 55-milestone boot gate still passes,
#       which is what rules out the conversions having quietly broken the
#       working architecture.
#   72  net/icmp.home and net/netdev.home added with STUB(S3)'s closure. Both
#       reached ARM64 codegen unchanged — the demux is byte-order and
#       structure work with no architecture-specific instruction in it, which
#       is what being written against the neutral intrinsics buys.
#   77  the crypto set joins Appendix A. Every one of these files is pure
#       integer arithmetic with no inline assembly in it, so ARM64 codegen
#       came free — which is the point of having written them that way.
#   78  curve25519.home. Its field arithmetic is ten signed limbs and nothing
#       else, so like the rest of the crypto set it reached ARM64 codegen with
#       no separate work.
#   79  drivers/acpi.home. Its table walking is byte arithmetic over physical
#       memory; only the port-I/O in shutdown is architecture-specific, and
#       that goes through foundation's wrappers.
#   80  fs/homefs.home. Its encode/decode is byte arithmetic and a blake2s
#       call, so ARM64 came free.
#   81  drivers/usb.home. Its register access goes through the neutral MMIO
#       intrinsics, so the discovery path lowers for ARM64 as it stands —
#       though no ARM64 machine in this tree presents an xHCI yet.
81
