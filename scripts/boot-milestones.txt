# the boot to count as unbroken. Each one is a subsystem that has been seen to
# initialize on real hardware emulation.

# green: a milestone that stops appearing means something that used to work
# has stopped working, which is exactly what this gate exists to catch.

# --- homefs on-disk structures (STUB(S4) step 1) ------------------------------
# docs/design/homefs.md §9 step 1 is "on-disk struct definitions + encode/decode
# unit tests". This is those tests run on the machine: a round trip through the
# byte layout, a torn write that must not read as valid, superblock slot
# selection, and a half-written commit record that must read as absent rather
# than as a transaction that happened.
[homefs] on-disk structures round-trip, 7/7
# Design doc §9 step 2: "executed tree tests". 600 keys against 254 entries per
# node forces the root to split, which is the case worth testing — a tree that
# never divides exercises none of the copy-on-write path through a parent.
# Every key is read back rather than a sample, because a tree that lost entries
# during a split still answers most lookups. The old root is checked to still
# describe the tree as it was, which is the property snapshots rest on.
[homefs] copy-on-write B-tree, 6/6
[homefs] objects, directories and extents, 12/12

# --- xHCI controller discovery (STUB(S6) groundwork) --------------------------
# Found on the PCI bus by class, its register window mapped and its capability
# registers read. What remains of S6 is above this: the command ring, the event
# ring, the device-context base array, and enumeration. Those are sized from
# the numbers read here, which is why this part had to be right first.
[USB] controller registers readable
# The controller reset, accepted its device-context array, command ring and
# event ring, and left the halted state. It either clears USBSTS.HCHalted or
# it does not, which is why this line is worth more than the one above it.
[USB] xHCI running, rings armed
# A No-Op command placed on our ring, the doorbell rung, and the controller's
# completion event read back off the event ring — naming our TRB, reporting
# success. That exercises the cycle bit, the doorbell and the dequeue pointer,
# which is the machinery every later command rides on.
[USB] command ring round trip: no-op completed
# A real device on a real port: reset acknowledged with the port enabled, then
# a slot allocated by an Enable Slot command. The slot number varies, so the
# milestone is the prefix — the same shape as the timer line above.
#
# The gate attaches a usb-hub rather than a usb-kbd on purpose: a USB keyboard
# takes keystrokes away from the PS/2 controller, which silences the
# "[IRQ] keyboard line live" milestone further down.
[USB] port reset, device enabled
[USB] slot 
# Address Device, then a control transfer on endpoint 0 reading the device
# descriptor. The identifiers are asserted in full rather than as a prefix:
# 0409:55AA is QEMU's hub, and a descriptor read that landed on the wrong
# bytes would still produce a plausible-looking prefix. If QEMU ever changes
# them, that is worth noticing deliberately rather than silently matching.
[USB] device addressed
[USB] descriptor read: 46F4:0001
# The gate's USB device is a usb-storage, not the usb-hub it used to be. The
# hub enumerated but could never move data — its only endpoint is an interrupt
# IN that reports port changes, and none happen during a boot. A mass-storage
# device has bulk endpoints, which is what makes the lines below possible.
#
# These milestones therefore replace the hub's rather than sitting beside
# them: same enumeration path, asserted against a device that can also be
# talked to. A usb-kbd would have been the other option and is still not
# usable here — it takes keystrokes away from the PS/2 controller and silences
# the keyboard milestone further down.
[USB] configuration 1, interface class 8
[USB] device configured
[USB] bulk endpoints configured, in 81 out 02
# Data moved on a non-control endpoint: a Command Block Wrapper out, the reply
# in, and a Command Status Wrapper whose signature, tag and status all had to
# match before the answer was believed. "QEMU" is the vendor field of the
# device's own INQUIRY response.
[USB] SCSI INQUIRY: QEMU
# READ CAPACITY(10) then READ(10) of LBA 0. The capacity is asserted because
# 4096 blocks of 512 is exactly the 2 MB image the harness builds, and the
# block contents because the harness wrote that signature into it — bytes
# coming back is not the same as the right bytes coming back, and only the
# second distinguishes a working read path from a plausible one.
[USB] capacity 4096 blocks of 512
[USB] block 0: HOMEOS-USB-BLOCK0

[Kernel] Entering main loop
[IRQ] timer=

# --- userspace -------------------------------------------------------------
# `run /bin/hello` maps a flat binary into user pages, drops to ring 3, and
# the program's write and exit arrive through int $0x80. The exit code is 7
# so a real return can be told from a default one.
hello from ring 3
[User] exit(7)

# `exec` goes through the ELF loader instead: the image says where its
# segments live and the loader maps them there. The data-segment line proves
# filesz bytes were actually copied — a segment that arrives blank looks the
# same as one that was never read.
hello from an ELF at ring 3
elf data segment intact
[User] exit(9)


# `disk` writes a pattern to the last sector and reads it back. A driver that
# reports a device it cannot actually carry a byte to is the failure worth
# catching, and it looks identical at init time.
